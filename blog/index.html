How we built a disease-risk demo without using real patient records

Meet SynthoCare Risk Lab — a simple project that creates fake but realistic health data, trains multi-disease risk models, and shares a live web app for learning and demos.

Easy-read blog for students, developers & educators · Reading time ~6 minutes

Please read first: This project uses synthetic (computer-generated) data only. The app is for education and research demos. It is not a medical device, not clinically validated, and must not be used to diagnose, treat, or make decisions about real patients.

Real medical records are private and hard to share. But people still need safe ways to practice healthcare machine learning. SynthoCare builds that practice sandbox—from data to models to a live website.

The problem in one sentence

If you want to learn how disease-risk models work, you need data that looks clinical— but you should not need to risk anyone’s privacy to get started.

How the pipeline works

You can think of the whole project as five clear steps:

  1. Generate synthetic data Code invents people, risk factors, disease progression, lab patterns, and delayed “observed” diagnoses.
  2. Split by person, not by row Train / validation / test sets keep each synthetic patient in only one bucket—so models are not tested on the same people they learned from.
  3. Train multi-disease models Each condition gets a risk head. Inputs include age, lifestyle, vitals, symptoms, family history, and optional labs.
  4. Export a tiny fast model Coefficients go into a small JSON file so the website can start quickly with lightweight libraries.
  5. Publish a Streamlit app Users fill a form, click run, and see ranked demo probabilities—with disclaimers on every important screen.

What the live app looks like

  • Home — project story and safety banner
  • Risk prediction — form for a “what-if” scenario
  • Model metrics — scores on held-out synthetic data
  • About & limits — intended vs prohibited uses

A high score only means: “In our synthetic training world, similar patterns often matched this label.” It does not mean a real person has that disease.

Then open http://localhost:8501.

Who should use this?

  • Students learning healthcare ML
  • Engineers practicing safe data pipelines
  • Teachers who need an interactive classroom demo
  • Builders prototyping risk-dashboard UX with non-sensitive data

Who should not use this for care?

  • Clinicians seeking decision support for real patients
  • Anyone expecting population statistics from a real country or hospital
  • Teams wanting regulatory-ready medical software out of the box

Four lessons worth remembering

Takeaways

  1. Privacy first — synthetic data lets you practice without exposing people.
  2. Split carefully — patient-level train/test splits fight leakage.
  3. Good metrics ≠ clinical usefulness — synthetic AUROC is not bedside proof.
  4. Label the product honestly — demos should shout limits as loudly as features.

FAQ

Is this real hospital data?

No. Every “patient” is generated by code for research and teaching.

Can this diagnose someone?

No. It is not clinically validated and is not for patient care.

Why multiple disease scores?

Chronic conditions often travel together. The demo shows multi-condition outputs, not one final diagnosis.

Why is the website sometimes slow?

Free Streamlit Cloud can cold-start or throttle CPU. That is hosting behavior. Local runs are usually smoother.

Can I reuse the code?

Yes. The repo is open on GitHub. Keep the synthetic-data disclaimer if you remix or republish the demo.

Final word

Healthcare AI needs safe places to learn. SynthoCare Risk Lab is one of those places: realistic enough for pipeline practice, honest enough to say “synthetic only — not for clinical use.”

Explore the live demo, read the code, break things, rebuild them—and when you move toward real-world health AI, bring the same discipline: privacy, careful evaluation, and external clinical validation.
